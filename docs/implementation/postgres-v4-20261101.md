## 失败原因与后续选择

官方 v4 源码 `src/pool.js:414–423` 在每次连接失败后安排下一次 backoff，再按当时经过时间判断connect_timeout是否到期；`grow():299–309` 可能等待跨过该时点，默认 `src/index.js:520–521` 的随机指数退避会放大等待。`failingFast():341–342` 还会在下一次尝试时间之前向新请求返回缓存的连接失败。这能解释本次有界结算和恢复新请求的差异；本轮没有修改官方包、缩短backoff热循环或放宽测试预算。

2026-11-01 只读核对官方 registry：`npm view postgres dist-tags` 的 `latest` 为 `4.0.0`，`npm view postgres@4 version` 也仅返回 `4.0.0`，与本轮已测版本一致。原结果保留于 `registry-dist-tags-20261101.json`、`registry-v4-versions-20261101.json`；没有安装其他版本。这只描述当次已发布4.x，不能推断上游未发布分支或以后版本也没有修正。

本轮所读 v4.0.0 [官方升级说明及选项](https://github.com/porsager/postgres/blob/v4.0.0/README.md)未提供独立的禁用重试/立即失败开关。`queue_timeout` 可以在未获得连接时移除排队的查询、事务或reserve并以 `QUEUE_TIMEOUT` 拒绝，官方声明这些工作未发送；它不约束已发送SQL，需配服务器statement_timeout，也不能独自解决失败缓存对恢复后新请求的影响。若采用此选项，应单独定义接入和恢复策略，并用原业务副作用、同池恢复及失败后无旧写入断言重新验证；不能只换错误码或放宽时间当作通过。

真正的公开配置适配至少涉及以下独立设计范围，当前均未实施：

- 为主查询、生成、音频和调度四个连接池分别确定排队预算，并定义 `QUEUE_TIMEOUT` 的对外错误及新请求重试规则。过短的预算也会拒绝健康数据库下因池满而等待的合法工作，不能直接把健康检查预算当作全部业务的排队预算。
- 区分“明确未发送”和“已发送但结果未知”。前者可按批准策略接受新的工作；后者仍按数据库statement_timeout、事务及持久任务栅栏处理，不能自动重放写入或费用任务，也不能以取消请求承诺事务未执行。
- 定义数据库恢复后的新请求策略，覆盖当前失败缓存与下一次连接尝试时间的关系。延后就绪、连接池重建或其他恢复措施会影响可用性、并发及进行中的事务，需要独立验证，不能只缩短backoff造成热重连。
- 重新执行全部FIN/RST、两槽五路并发、健康冷启动、同池新请求恢复、已失败旧注册无晚到写入以及错误分类回归。原业务副作用和时间保证须保留；任何确需改变的外部契约要另行明确批准，不在依赖维护中悄悄改断言。
