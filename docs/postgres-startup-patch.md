# PostgreSQL 驱动启动断连补丁

## 问题与范围

锁定的 `postgres@3.4.9` 在初次握手遇到持续正常关闭（TCP FIN）时，`closed()` 会在初始请求仍存在的情况下直接重连。每次关闭取消连接计时器，下次重连又重新计时，因此 `connect_timeout` 没有约束整个过程。初次请求可能持续 pending，注册服务也可能在之后恢复时继续写入。

来源：[上游 #1193](https://github.com/porsager/postgres/issues/1193)、[类型加载状态 #1223](https://github.com/porsager/postgres/issues/1223)、[待审提案 #1241](https://github.com/porsager/postgres/pull/1241)。本地实现没有将该提案当作已经发布的官方修复，也没有直接复制其仍存在的 reservation 残余问题。

本项目选择：启动连接关闭即失败当前请求；终态拒绝并清理初始请求、内部类型加载、已发送队列和连接池归属。一个预留连接请求只存在于连接或等待队列中的一处，避免已经拒绝的预留请求在恢复后被再次取得。后续的新请求可以重新连接。

## 可重复安装

`scripts/apply-postgres-startup-patch.mjs` 从 `patches/` 读取最小 diff 和四个输入 / 输出 SHA256，核对实际包名、精确版本及 lock integrity。它先检查所有文件和计算后的输出，再修改 Node ESM/CJS 的 `connection.js`、`index.js`。

- 原始已知源码：按 diff 应用并核对结果哈希。
- 已经修补的已知源码：幂等验证。
- 已知的混合状态：重新运行可补齐。
- 未知版本、内容或 integrity：失败，不猜测上下文。

四个文件分别以临时文件重命名替换，不是跨文件磁盘事务。若中途发生 I/O 错误，安装返回失败；重新运行前应确认仍为已知的原始 / 修补哈希组合，不能忽略安装错误启动应用。

Root `npm ci` 会执行 `postinstall`；两个 Dockerfile 在开发依赖和生产依赖安装之前都复制同一安装器与补丁。安装器不依赖开发包。禁止把一次手工修改 `node_modules` 当作交付：干净安装和容器依赖阶段必须能复现。

## 实际验收

默认 API 集成套件包含 EOF 恢复回归：

- 初次握手和真实 `pg_catalog.pg_type` 加载期间的 FIN。
- Node ESM / CJS 入口；普通查询、`reserve()`、`begin()`、Drizzle 事务。
- 连接池 2 槽、5 路并发，失败期间业务段不执行；恢复后只执行新操作。
- 没有未处理拒绝、没有残余重连；同一个连接池可恢复。
- 健康冷启动的预留 / 释放，以及枚举数组、整数数组解析。
- 真实 API 的并发注册有界失败；恢复并等待超过原连接预算后，旧请求未新增 users / frequencies；新注册和 deep health 成功。

工具测试另验证原始源码应用、幂等、混合状态修复、源码漂移前零修改和版本拒绝。独立诊断保留修复前的 pending 失败记录；它的人工观察窗口不是线上性能指标。

## 边界与维护

当前项目使用单 PostgreSQL 主机配置。多主机、`target_session_attrs`、Deno / Cloudflare 入口没有在本轮验证。启动抖动会更早向当前请求报告错误，替代此前的透明重试；业务层可针对新请求选择受控重试。

本补丁不保证已经开始的事务回调停止，也不解决 COMMIT 已提交但回执丢失的结果不确定性。不能以 HTTP `Promise.race` 或尽力取消，承诺任意超时都没有发生写入。身份镜像写入事务、生成任务领取 / 幂等和更完整的恢复治理仍属于后续任务。

上游发布修复后，须先对照该回归集验证行为，再解除版本固定、删除 `postinstall` / 安装器 / 补丁及对应 Docker COPY。回滚也应成组恢复这些文件并干净安装；原始 3.4.9 会重新暴露该 EOF 缺陷。没有生产迁移或生产数据变更。
